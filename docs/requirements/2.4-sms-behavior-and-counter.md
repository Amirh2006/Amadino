# Phase 2.4 — SMS Behavior, Error Handling, and SMS Counter Limits

## Goal
Define exactly how entry/exit SMS notifications work, how failures and fallbacks are handled, and how the SMS sent counter is tracked and limited.

---

## 1. SMS Trigger Events

| Event | When | Default Message Template |
|-------|------|--------------------------|
| ENTRY | Student attendance recorded as PRESENT or LATE for a class time | `"{studentName} entered class at {time} on {date}."` |
| EXIT | Student leaves / attendance closed for the class time | `"{studentName} exited class at {time} on {date}."` |

- SMS is sent per student per event (entry/exit), using the student's registered mobile numbers.
- Message templates are configurable in a settings screen (Phase 7), with sensible defaults.
- SMS sending is optional per student: if neither mobile number is valid, no SMS is attempted (logged as SKIPPED).

---

## 2. Destination & Fallback Logic

**R-SMS-01:** Primary destination is `student.mobile1`.

**R-SMS-02:** If sending to `mobile1` fails (error result from `SmsManager`), the system automatically retries once to `student.mobile2` (if present).

**R-SMS-03:** If both fail, the message is logged as FAILED with the last error reason.

**R-SMS-04:** Fallback is attempted only once per event — no infinite retries.

**R-SMS-05:** If `mobile2` is absent and `mobile1` fails, log FAILED immediately.

---

## 3. SMS Log Entity

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| id | Integer | Yes | Primary key |
| studentId | Integer | Yes | Student the SMS relates to |
| attendanceId | Integer | No | Related attendance record (if any) |
| eventType | Enum | Yes | ENTRY / EXIT |
| destination | String | Yes | The phone number actually used |
| messageBody | String | Yes | The SMS text sent |
| status | Enum | Yes | SUCCESS / FAILED / SKIPPED / PENDING |
| errorReason | String | No | Failure reason (e.g., "No SIM", "Generic failure", "Radio off") |
| sentAt | DateTime | Yes | Timestamp of the attempt |
| fallbackUsed | Boolean | Yes | True if mobile2 was used |

---

## 4. Error Handling Matrix

| Condition | Behavior | Log Status |
|-----------|----------|------------|
| SEND_SMS permission not granted | Prompt for permission; do not send | SKIPPED (permission) |
| No SIM card / no service | Attempt fails; log reason | FAILED |
| `mobile1` invalid/empty | Skip to `mobile2` if present, else SKIPPED | SKIPPED / FAILED |
| `mobile1` send fails (generic) | Fallback to `mobile2` | FAILED (mobile1) then attempt mobile2 |
| `mobile2` also fails | Log final failure | FAILED |
| Airplane mode / radio off | Fail fast; log reason | FAILED |
| SMS length > 160 chars | Split into multipart SMS (allowed) | SUCCESS (if delivered) |
| Device offline (no network for delivery report) | SMS queued by system; log PENDING | PENDING |

---

## 5. SMS Counter

### 5.1 What Is Counted
- The **SMS sent counter** increments by **1 for every successfully submitted SMS segment** (a multipart message counts per segment).
- Failed attempts do **not** increment the success counter, but are tracked separately (attempt count).

### 5.2 Counter Entity

| Field | Type | Description |
|-------|------|-------------|
| id | Integer | Primary key (single-row counter) |
| totalSent | Integer | Total successfully sent SMS segments |
| totalFailed | Integer | Total failed attempts |
| totalSkipped | Integer | Total skipped attempts |
| lastUpdated | DateTime | Last counter update |

### 5.3 Counter Limits

| Rule ID | Rule |
|---------|------|
| C-01 | The counter is a lifetime cumulative count, displayed live in the UI. |
| C-02 | Optional monthly reset for reporting; lifetime total is never lost. |
| C-03 | A configurable **soft warning threshold** (default: 1000 SMS) triggers a UI warning when exceeded. |
| C-04 | No hard block by default — the app must never silently stop sending without warning the administrator. |
| C-05 | The counter updates transactionally with each SMS log entry (no drift). |

---

## 6. Permission Handling

**R-PERM-01:** `SEND_SMS` is a dangerous permission requested at runtime before the first send attempt.

**R-PERM-02:** If denied, the app shows an explanation and a button to open app settings.

**R-PERM-03:** SMS sending must never crash the app; all `SmsManager` calls are wrapped in try/catch.

**R-PERM-04:** `READ_PHONE_STATE` is not required for basic sending; avoid requesting unnecessary permissions.

---

## 7. Scenarios

**SC-SMS-01: Send entry SMS on attendance**
- Attendance recorded PRESENT → system builds ENTRY message → sends to mobile1 → on success logs SUCCESS and increments counter.

**SC-SMS-02: Fallback on failure**
- mobile1 fails → system retries to mobile2 → success logs SUCCESS (fallbackUsed=true), counter +1.

**SC-SMS-03: Both numbers fail**
- mobile1 fails, mobile2 fails → log FAILED with reason, counter not incremented for success, failed count +1.

**SC-SMS-04: Missing permission**
- User denies SEND_SMS → attempt logged SKIPPED (permission), no counter increment, UI shows guidance.

**SC-SMS-05: View SMS counter**
- Dashboard/Settings shows totalSent, totalFailed, totalSkipped, and lastUpdated in real time.

---

## 8. Acceptance Criteria (Phase 2.4)

- [ ] Entry and exit SMS are triggered per student per attendance event.
- [ ] Primary destination is mobile1; fallback to mobile2 on failure (single retry).
- [ ] Every attempt is logged with status, destination, message, error reason, timestamp, fallbackUsed.
- [ ] SMS sent counter increments per successful segment and updates transactionally.
- [ ] Failed/skipped attempts are tracked separately.
- [ ] Soft warning threshold (configurable) displayed; no silent hard block.
- [ ] SEND_SMS runtime permission handled gracefully; no crashes.
- [ ] All SmsManager calls wrapped in try/catch.
