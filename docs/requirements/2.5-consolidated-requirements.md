## 1. Product Summary

Amadino is a local-first Android app for a single school administrator managing 50–60 students. It records attendance per class time, manages weekly days/shifts/monitors, tracks tuition and debt, and sends entry/exit SMS to parents via the device SIM. No servers, no external SMS panels.

## 2. Domain Model

### 2.1 WeekDay
- `id`, `name`, `code`, `isSchoolDay`, `sortOrder`
- Only school days can host shifts. Unmarking a day deactivates (not deletes) its shifts.

### 2.2 Shift
- `id`, `dayId`, `name`, `startTime`, `endTime`, `monitorName`, `isActive`
- Belongs to a school day; must contain ≥1 class time; no overlapping shifts on the same day.

### 2.3 ClassTime
- `id`, `shiftId`, `name`, `startTime`, `endTime`, `sortOrder`
- Must fall within shift bounds; no overlap within a shift.

### 2.4 Student
- `id`, `fullName`, `fatherName`, `nationalId?`, `grade`, `mobile1`, `mobile2?`, `totalTuition`, `currentDebt`, `isActive`, `createdAt`, `updatedAt`
- `mobile1` mandatory; `mobile2` fallback. `0 <= currentDebt <= totalTuition`. Debt initializes to tuition. Payments reduce debt (clamped at 0). `nationalId` unique if provided.

### 2.5 Attendance
- `id`, `studentId`, `classTimeId`, `shiftId`, `dayId`, `attendanceDate`, `status` (PRESENT/ABSENT/LATE), `recordedAt`, `recordedBy?`
- **Unique:** `(studentId, classTimeId, attendanceDate)` — one record per student per class time per day.
- Only active shifts on school days; no future dates; upsert on re-save.

### 2.6 SmsLog
- `id`, `studentId`, `attendanceId?`, `eventType` (ENTRY/EXIT), `destination`, `messageBody`, `status` (SUCCESS/FAILED/SKIPPED/PENDING), `errorReason?`, `sentAt`, `fallbackUsed`

### 2.7 SmsCounter (single row)
- `totalSent`, `totalFailed`, `totalSkipped`, `lastUpdated`
- Increments per successful segment; transactional with log writes; configurable soft warning (default 1000); no silent hard block.

## 3. Key Business Rules

| ID | Rule |
|----|------|
| BR-01 | Shifts exist only on school days. |
| BR-02 | Each shift has ≥1 class time; class times cannot overlap within a shift. |
| BR-03 | Shifts cannot overlap on the same day. |
| BR-04 | Attendance is recorded per student **per class time** (not per day). |
| BR-05 | `(studentId, classTimeId, attendanceDate)` is unique; re-save updates. |
| BR-06 | No attendance for future dates; only active shifts/school days. |
| BR-07 | `mobile1` mandatory; SMS falls back to `mobile2` once on failure. |
| BR-08 | Every SMS attempt is logged; counter updates transactionally. |
| BR-09 | Failed/skipped SMS never crash the app; SEND_SMS permission handled at runtime. |
| BR-10 | `0 <= currentDebt <= totalTuition`; payments clamp debt at 0. |
| BR-11 | Deactivating shifts/days preserves historical records. |
| BR-12 | All data stored locally on device (Room/SQLite). |

## 4. User Scenarios (Summary)

1. **Setup:** Configure school days, create shifts with monitor names, add class times.
2. **Enroll:** Add students with dual mobiles, tuition, auto-initialized debt.
3. **Attendance:** Pick day → active shift → class time → mark students PRESENT/ABSENT/LATE; save (upsert).
4. **Notify:** Entry/exit SMS to mobile1, fallback mobile2; log result; update counter.
5. **Finance:** Record payments, view debtors list, adjust tuition.
6. **Reports:** Filter attendance by day/shift/class time/date/status; view SMS counter and logs.
7. **Backup:** Local database backup/restore.

## 5. Non-Functional Requirements

| ID | Requirement |
|----|-------------|
| NFR-01 | Offline-first; no internet dependency for core features. |
| NFR-02 | Fast UI for 50–60 students (list rendering, quick attendance). |
| NFR-03 | Local data privacy; no external transmission except SMS via SIM. |
| NFR-04 | Simple, maintainable architecture (ViewModel + Repository, Room). |
| NFR-05 | Testable business logic (attendance dedup, debt calc, SMS fallback). |
| NFR-06 | Graceful error handling (SMS, permissions, missing SIM). |

## 6. Acceptance Criteria (Phase 2 overall)

- [ ] Weekly days configurable (school day toggle).
- [ ] Shifts with monitor, times, active flag, and ≥1 non-overlapping class time.
- [ ] Students with mobile1 (required), mobile2 (optional), tuition, debt (≤ tuition).
- [ ] Attendance per class time with duplicate prevention (upsert).
- [ ] SMS entry/exit with mobile1→mobile2 fallback and full logging.
- [ ] SMS counter (sent/failed/skipped) with soft warning.
- [ ] Debtors list and payment recording.
- [ ] All data local; app works offline.

## 7. Open Questions for User Approval

1. **Currency unit:** Should amounts be stored in Toman (integer) or Rial? (Default assumption: Toman, integer, no decimals.)
2. **SMS on ABSENT:** Should an SMS be sent when a student is marked ABSENT (e.g., "absent notice"), or only on ENTRY/EXIT?
3. **Exit SMS trigger:** Is "exit" a manual action, or auto-sent at class-time end? (Default assumption: manual "close/exit" action per class time.)
4. **Multiple shifts per day per student:** Can a student belong to more than one shift? (Default assumption: student is assigned to one shift; filter logic in Phase 6.)
5. **Default SMS text language:** Persian or English? (Default assumption: configurable template, Persian default for the target school.)
